## A. Code Simplification & Standards Violations

### A1. `cli.py` is 1,327 lines — must be split (Priority: HIGH)

**Standard:** ≤500 lines per file.  
`cli.py` is 2.6× over the limit. It mixes entry-point setup, Rich rendering helpers, slash command handlers, threaded/sync agent dispatch, subagent orchestration, plan mode, hist output, and piped-mode detection all in one file.

**Suggested split** (mirrors the `tui/` package pattern that already worked):
```
cli/
  __init__.py        — re-export public entry points
  rendering.py       — _colour(), _truncate(), _TOOL_COLOURS, Rich panel helpers
  callbacks.py       — build_callbacks() (analogous to tui/callbacks.py)
  commands.py        — slash command handlers (_cmd_help, _cmd_hist, _cmd_model, etc.)
  dispatch.py        — _run_task(), threaded/sync runner, plan mode orchestration
  main.py            — typer app + @app.command() entry point
```
Root `cli.py` becomes a ~30-line launcher identical to `tui.py`.

**Why this matters:** The file can't be reviewed in one pass, makes test targeting hard, and violates a stated coding standard the Admiral enforces consistently.

### A2. `agent/loop.py` is 889 lines — extract retry and sentinel logic (Priority: MEDIUM)

The API retry block (transient errors + ghost responses) spans ~100 lines inline inside `run()`. The sentinel dispatch (ENTER_PLAN_MODE, EXIT_PLAN_MODE, RELOAD_SKILLS, SWITCH_MODEL) is another ~150 lines.

**Suggested extractions:**
- `agent/_api_call.py` — `_api_call_with_retry(client, model, messages, tools, extra_body, config, callbacks) -> response | None (paused)`
- `agent/_sentinel_handlers.py` — `_handle_sentinel(result, ...)` returning an enum `SentinelAction` consumed by the caller

This brings `loop.py` under 600 lines without changing any behavior. Each extracted module has a single concern and is easier to unit-test.

### A3. `create_tool_registry()` plan-mode vs normal-mode branching is hard to follow (Priority: MEDIUM)

`agent/tools.py:create_tool_registry()` is a 150-line if/else with deeply nested branches for plan_mode=True and plan_mode=False. The two branches share nothing except the file tools at the top.

**Suggestion:** Introduce two private helpers:
```python
def _register_plan_mode_tools(reg, ...) -> None: ...
def _register_normal_mode_tools(reg, ...) -> None: ...
```
`create_tool_registry()` becomes: register file tools → call the appropriate helper → `filter_to` → return. Reduces cyclomatic complexity and makes it obvious which tools are available in each mode.

### A4. `_tools_from_list()` for subagents is a maintenance hazard (Priority: LOW-MEDIUM)

`_tools_from_list()` (used by `build_subagent_registry`) has its own hardcoded `registry_map` dict of name→tool. If you add a new tool to the main registry or rename one, you must update this second map manually. There is no compile-time link between the two.

**Suggestion:** Drive subagent tool instantiation from the same factory as the main registry. One option: `create_tool_registry()` accepts a `tool_names: list[str] | None` that acts as a filter (replacing `filter_to` post-build), and `_tools_from_list` is deleted. Subagent registries call `create_tool_registry(tool_names=[...], ...)` directly.

## B. Architecture Improvements

### B1. System prompt has 3 build sites with no central assembly (Priority: MEDIUM)

`AgentLoop.__init__`, `_rebuild_for_normal_mode`, and `_rebuild_for_plan_mode` all independently build the system prompt string. PROJECT_CONTEXT.md notes: *"If a future refactor introduces a 4th build site, the same prefix pattern must be applied — there is no central assembly point."*

**Suggestion:** Extract `_build_system_prompt(config, registry, skills, dagi_root, mode="normal"|"plan") -> str` as a free function (or a `SystemPromptBuilder` class). All three sites call it. Removes ~100 lines of duplication and eliminates the class of bug where one rebuild site forgets to inject preamble/soul.

---

### B2. Compaction uses the default model — consider cheaper worker model (Priority: MEDIUM)

`CompactTool.compact()` calls `self._client.chat.completions.create(model=config.model, ...)` — it uses the same model as the main task. Compaction is a summarisation task, not reasoning; a `worker_config` tier model would be cheaper and equally effective.

**Suggestion:** Accept `compact_model: str | None` in `CompactTool.bind()`, defaulting to `config.model`. Populate it from `config.worker_config.model` in `AgentLoop.__init__`. This is a pure token-efficiency win with no behavior change.

---

### B3. Sidebar emote reads disk on every `render()` call (Priority: LOW)

`Sidebar._status_col()` calls `_load_face()` on every refresh, which opens and reads a file from `.dagi/emotes/`. The Textual render loop can fire many times per second. The file almost never changes between refreshes.

**Suggestion:** Cache the face text as `self._face_text: str` on `update_emote()` and return the cached value in `_load_face()`. Only re-read from disk when the emote name changes.

---

### B4. Subagent poller uses `time.sleep(_POLL_INTERVAL)` — use `proc.wait(timeout=)` (Priority: LOW)

`tools/_subagent_runner.py:_poll_until()` calls `proc.poll()` + `time.sleep(2.0)` in a loop. `subprocess.Popen.wait(timeout=2.0)` accomplishes the same with less CPU overhead (OS wakes the thread when the process exits instead of spinning every 2 seconds).

```python
try:
    proc.wait(timeout=min(_POLL_INTERVAL, deadline - time.monotonic()))
except subprocess.TimeoutExpired:
    pass  # still running, check deadline
```

---

### B5. TUI plan poll runs every 2 s even with no active loop (Priority: LOW)

`DagiApp._poll_plan()` is called unconditionally every 2 s by `set_interval`. It reads `loop.config.plan_file` from the active loop — but returns early if `self._active_loop is None`. The timer is never paused. On long idle sessions this creates unnecessary scheduler overhead.

**Suggestion:** The `set_interval` callback itself is nearly free, so this is cosmetic. But alternatively, start the plan poll only when a session is dispatched and cancel it on `/clear`.

## C. Token Efficiency & Self-Improvement

### C1. Cache hit tokens not visible anywhere (Priority: HIGH)

`cache_prompt: True` is already sent to OpenRouter, but `session.py` and the TUI sidebar never read `usage.prompt_tokens_details.cached_tokens` from API responses. Users have no visibility into whether prompt caching is working or what the savings are.

**Implementation:**
1. In `session.py:record_assistant()`, extract `cached_tokens = getattr(getattr(usage, "prompt_tokens_details", None), "cached_tokens", None)` and store it on `MessageNode` as a new optional field.
2. Pass `cached_tokens` through `on_token_update` callback (add a 5th argument).
3. In `tui/sidebar.py:_tokens_context_col()`, show a `cached` row in the context table when non-zero.

This makes the ROI of prompt caching visible and helps tune `keep_recent_tokens` / `reserve_tokens`.

### C4. No structured tool-argument validation before dispatch (Priority: MEDIUM)

`ToolRegistry.dispatch()` calls `json.loads(tc.function.arguments)` and passes kwargs directly to `tool.run()`. If the model produces invalid arguments (wrong types, missing required fields), the tool raises an unstructured exception caught as `f"Error: {e}"` — the model gets a terse error with no guidance.

**Suggestion:** In `registry.dispatch()`, validate kwargs against `_parameters` JSON Schema before calling `run()`. Use `jsonschema.validate()` (already available via PyYAML install chain) and return a structured `"Error: invalid argument '{field}': {reason}. Expected schema: ..."` message. This gives the model actionable feedback and reduces retry loops.

### C5. Continuation count per task is the primary waste signal — surface it (Priority: LOW)

The `_continuation_count` resets per `run()` call and is available on the loop, but is never logged or surfaced. High continuation counts indicate the model is not terminating cleanly — a prompt quality signal.

**Suggestion:** Add `continuations: int` to the `session_end` JSONL record in `SessionTracker.finish()`. Add a `/stats` slash command that shows: total tokens, cost, tool calls, and continuation count for the current session.

### D3. Parallel subagent dispatch (Priority: MEDIUM)

The `[~]` in-progress marker and the `_active` dict in `_subagent_runner.py` were designed with parallelism in mind. The parent loop can already call `spawn_*` multiple times; `_active` already supports multiple PIDs.

**Missing piece:** The parent agent needs prompting to dispatch multiple subagents in one turn rather than sequentially. The TUI's relay callback system handles concurrent event streams correctly.

**Implementation path:**
1. Add a `spawn_parallel_subagents` tool that accepts a list of `{type, task}` dicts and dispatches all of them, returning a list of PIDs.
2. Add a `wait_subagents(pids: list[int], timeout_per: int)` tool that polls all PIDs and collects handoffs.
3. Update the plan-work-review skill to use these when subtasks are independent.

## E. Testing & Quality

### E1. RAM watchdog threshold is hardcoded at 70% (Priority: MEDIUM)

`tests/conftest.py` hardcodes `0.70` and `0.90` thresholds. On a 31 GB machine with Claude Code + IDE + browser, idle RAM already exceeds 70%, causing all tests to fail in setup (not test body). There is no escape hatch.

**Fix:** Read threshold from env: `DAGI_RAM_WARN_PCT` (default 70) and `DAGI_RAM_KILL_PCT` (default 90). A one-line change: `_WARN_PCT = int(os.getenv("DAGI_RAM_WARN_PCT", "70")) / 100`. Add to `README.md` under "Running Tests".

---

### E2. No integration tests — only mocked unit tests (Priority: MEDIUM)

PROJECT_CONTEXT.md notes this explicitly. All 124 tests mock the LLM client. A real agent loop test that uses a recorded HTTP fixture (e.g., `pytest-recording` / `vcrpy`) would catch regressions that unit tests miss (e.g., the ghost-response cascade, sentinel parsing, compaction trigger).

**Suggested first integration test:** A session that:
1. Sends a task.
2. Gets a tool-call response (fixture).
3. Dispatches the tool.
4. Gets a final `<<END_OF_RESPONSE>>` response.
5. Asserts the session log is well-formed and `run()` returns the clean text.

No live API needed — `vcrpy` records a cassette once against a real endpoint, then replays deterministically.

### E3. DagiAgent adapters (Terminal-bench, Harbor) have zero test coverage (Priority: LOW)

`benchmarks/terminal_bench/agent.py` and `benchmarks/harbor/agent.py` — the two benchmark entry points — have no unit tests. A rogue change to `AgentLoop.__init__` signature or `resolve_model_config` could break both adapters silently until a benchmark run is attempted.

**Fix:** Add `tests/test_benchmark_adapters.py` with mock `perform_task()` calls for both adapters, verifying they instantiate and configure correctly without touching Docker or OpenRouter.

## F. Consistency Issues

### F1. Slash command handling is duplicated across CLI and TUI (Priority: MEDIUM)

`cli.py` has ~400 lines of slash command handlers (`/help`, `/clear`, `/hist`, `/model`, `/plan`, `/compact`, `/skill`, etc.) that parallel `tui/commands.py:SlashCommandsMixin`. The two diverge: TUI uses `SlashCommandsMixin` mixing into `DagiApp`; CLI has standalone functions. When a new slash command is added (e.g., `/project`), it must be added in both places.

**Suggestion:** Extract shared slash-command logic into a `cli/commands.py` module with pure functions (no TUI/Rich coupling). `cli.py` calls them directly; `tui/commands.py` calls the shared functions for the subset of commands that are identical. CLI-only commands (piped mode, raw output) stay in CLI; TUI-only commands stay in TUI.

---

### F2. Tool colors defined in two places (Priority: LOW)

`_TOOL_COLOURS` is defined in `cli.py` (line ~55) and a separate `_TOOL_COLOURS` in `tui/utils.py`. They diverge: the CLI has 6 entries, the TUI likely has a different set. Adding a new tool color requires updating both.

**Fix:** Move `_TOOL_COLOURS` to `agent/constants.py` (or `tools/_colours.py`) and import it in both `cli.py` and `tui/utils.py`.

---

### F3. `pyproject.toml` still missing core deps (Priority: LOW)

`typer`, `rich`, `textual` are not declared in `pyproject.toml`. `pip install -e .` on a clean environment fails silently (the conda env has them, but a new contributor using `pip install -e .` alone would hit ImportError. `requirements.txt` correctly lists them but `pyproject.toml` is the canonical source for `pip install -e .`.

**Fix (one commit):** Add to `pyproject.toml` dependencies: `"typer>=0.9"`, `"rich>=13"`, `"textual>=0.80"`. Remove dead deps: `"nicegui"`, `"markdown"`, `"matplotlib"`.
