## A. Bugs & Critical Issues

### A1. TUI never calls `loop.finish()` — session logs never finalized (Priority: CRITICAL)

**Files:** [`tui/app.py:147-161`](tui/app.py:147)

The CLI calls `loop.finish()` at **6 separate sites** (lines 975, 1107, 1240, 1246, 1271, 1309, 1313 in `cli.py`), `main.py` calls it at line 41, and `benchmarks/harbor/agent.py` calls it at line 79. But `_agent_work()` in the TUI never calls it — the `finally` block only sets status to "idle" and re-enables input.

**Impact:** `SessionTracker.finish()` writes the `session_end` JSONL record containing total tokens, cost, and tool call counts. Without it, every TUI session produces an incomplete log (missing the summary record), and the cost/token totals from subagents are never rolled up into the root tracker.

**Fix:** Add `loop.finish()` in the `_agent_work` finally block:
```python
finally:
    if loop_ref:
        loop_ref[0].finish()
    self.call_from_thread(sidebar.set_status, "idle")
    self.call_from_thread(self._enable_input)
```
Note: `finish()` is idempotent for the JSONL write — but the `raw_messages` snapshot should only be taken once. Guard with a `_finished` flag on the tracker if needed.

### A2. Soul/agents.md dropped from system prompt after plan-mode transitions (Priority: HIGH)

**File:** [`agent/loop.py:747-862`](agent/loop.py:747)

`__init__` assembles the system prompt with a `preamble_parts` list (lines 276–293) containing: `system_prompt_preamble`, `soul.md`, `dagi agents.md`, and `project agents.md`. Both `_rebuild_for_normal_mode` (line 789) and `_rebuild_for_plan_mode` (line 854) only re-inject `system_prompt_preamble` — they skip soul.md and both agents.md files entirely.

**Impact:** After entering plan mode and returning to normal mode, the agent loses its persona (soul.md) and behavioral guidelines (agents.md) from the system prompt. The system prompt for the rest of the session contains only the raw `main_system.md` template + preamble. This silently degrades agent behavior for the entire remainder of a plan-mode session.

**Fix:** Extract the preamble assembly into a shared method:
```python
def _build_preamble(self, dagi_root: Path) -> str:
    parts: list[str] = []
    if self.config.system_prompt_preamble:
        parts.append(self.config.system_prompt_preamble.strip())
    soul_text = load_soul(dagi_root, self.config.project_path)
    if soul_text:
        parts.append(soul_text.strip())
    for agents_path in [
        dagi_root / ".dagi" / "agents.md",
        self.config.project_path / ".dagi" / "agents.md",
    ]:
        if agents_path.exists():
            text = agents_path.read_text(encoding="utf-8").strip()
            if text:
                parts.append(text)
    return "\n\n---\n\n".join(parts)
```
Call it from `__init__`, `_rebuild_for_normal_mode`, and `_rebuild_for_plan_mode`. This also addresses the long-standing "3 build sites with no central assembly" issue from prior reviews (B1 in 2026-06-16 todo).

### A3. `json.loads(tc.function.arguments)` parsed up to 4 times per tool call (Priority: MEDIUM)

**File:** [`agent/loop.py:547-562`](agent/loop.py:547)

In the tool dispatch loop, `json.loads(tc.function.arguments)` is called:
1. Line 547: `self.registry.dispatch(tc.function.name, json.loads(...))`
2. Line 550: `self._handle_enter_plan_mode(json.loads(...))`
3. Line 552: `self._handle_exit_plan_mode(json.loads(...))`
4. Line 562: `self._handle_switch_model(_switch_target, json.loads(...))`

The same string is parsed multiple times per tool call. Lines 550/552/562 re-parse it after the dispatch already parsed it on line 547.

**Impact:** Wasted CPU (minor) but more importantly, if `tc.function.arguments` contains malformed JSON, the dispatch on line 547 will fail first and return an error string — but the sentinel checks on lines 549–562 will then try to parse the same bad JSON again, raising an unhandled `json.JSONDecodeError` that propagates as an uncaught exception instead of a clean tool error.

**Fix:** Parse once at the top of the loop:
```python
try:
    tool_kwargs = json.loads(tc.function.arguments)
except json.JSONDecodeError as e:
    result = f"Error: invalid JSON in tool arguments: {e}"
    # skip dispatch, append error result
    ...
    continue
result = self.registry.dispatch(tc.function.name, tool_kwargs)
if isinstance(result, str) and result.startswith(ENTER_PLAN_MODE_SENTINEL):
    result = self._handle_enter_plan_mode(tool_kwargs)
...
```

### A4. `ENTER_PLAN_MODE_SENTINEL` uses prefix check while others use equality (Priority: MEDIUM)

**File:** [`agent/loop.py:549-555`](agent/loop.py:549)

```python
if isinstance(result, str) and result.startswith(ENTER_PLAN_MODE_SENTINEL):  # prefix
elif result == EXIT_PLAN_MODE_SENTINEL:    # exact
elif result == COMPLETE_PLAN_SENTINEL:     # exact
elif result == RELOAD_SKILLS_SENTINEL:     # exact
```

Line 549 uses `startswith()` while lines 551, 553, 555 use `==`. If a tool accidentally returns a string starting with the enter sentinel (e.g., a tool result that includes the sentinel text in an error message), plan mode would be triggered erroneously.

**Fix:** Either use exact `==` for all sentinels, or document why `startswith` is needed for this specific case (perhaps it carries payload data after the sentinel).

## C. Token Efficiency & Self-Improvement

### C1. `SkillLoader.rglob("SKILL.md")` recurses into all subdirectories (Priority: MEDIUM)

**Files:** [`agent/skills.py:67`](agent/skills.py:67), [`agent/skills.py:79`](agent/skills.py:79)

```python
for skill_file in sorted(root.rglob("SKILL.md")):
```

`rglob` recurses into ALL subdirectories including `.git/`, archived drafts, nested skill directories, or user data. This differs from the expected `<root>/<skill-name>/SKILL.md` one-level pattern. A stray `SKILL.md` buried deep in a git-tracked dependency or user data directory would be loaded as a skill.

**Fix:** Use `root.glob("*/SKILL.md")` for one-level depth, or add an exclude filter for `.git` and common noise directories.

### C3. `on_ask_user` default callback crashes on empty options list (Priority: LOW)

**File:** [`agent/loop.py:163-168`](agent/loop.py:163)

```python
on_ask_user: ... = field(
    default=lambda question, options, timeout: next(
        (o["label"] for o in options if o.get("recommended")),
        options[0]["label"] if options else "",
    )
)
```

The `next(...)` call with a default value of `options[0]["label"] if options else ""` is evaluated eagerly as the default argument to `next()`, not lazily. So when `options` is non-empty but no option is `recommended`, it returns `options[0]["label"]` correctly. But the structure is confusing and a maintenance hazard — the conditional `if options else ""` only guards the default expression, not the generator.

This is not a bug per se (it works correctly), but the logic is harder to read than it needs to be for a safety-critical default path.

### D2. Structured error result from `ToolRegistry.dispatch()` (Priority: MEDIUM)

**File:** [`agent/registry.py:29-35`](agent/registry.py:29)

```python
def dispatch(self, name: str, kwargs: dict) -> str | list:
    if name not in self._tools:
        return f"Error: unknown tool '{name}'"
    try:
        return self._tools[name].run(**kwargs)
    except Exception as e:
        return f"Error: {e}"
```

The `except Exception as e` catches all exceptions but returns only `str(e)`. For many exceptions (especially `TypeError` from wrong kwargs, `FileNotFoundError`, etc.), the string representation is terse and unhelpful to the LLM.

**Fix:** Include the exception type and, for `TypeError` (wrong arguments), list the tool's expected parameters:
```python
except TypeError as e:
    params = list(self._tools[name]._parameters.get("properties", {}).keys())
    return f"Error ({type(e).__name__}): {e}. Expected parameters: {params}"
except Exception as e:
    return f"Error ({type(e).__name__}): {e}"
```

## E. Consistency & Quality

### E1. `BashTool.run()` has no negative timeout guard (Priority: LOW)

**File:** [`tools/bash.py:25-33`](tools/bash.py:25)

`timeout` parameter is typed `int | None` but not validated. If the LLM passes `timeout=0` or `timeout=-5`, `subprocess.run()` raises `ValueError: timeout must be positive` — which is caught by `ToolRegistry.dispatch()` as a generic `Error: ...` with no guidance for the LLM.

**Fix:** Clamp or validate: `timeout = max(1, timeout) if timeout is not None else None`

### E2. `ReadTool` has no encoding error handling (Priority: LOW)

**File:** [`tools/read.py:49`](tools/read.py:49)

```python
lines = p.read_text(encoding="utf-8").splitlines()
```

A file with non-UTF8 encoding (e.g., Latin-1 config files, binary files with a `.txt` extension) will raise `UnicodeDecodeError`. The exception propagates to `registry.dispatch()` which returns a terse `"Error: ..."`.

**Fix:** Add `errors="replace"` to gracefully handle encoding issues:
```python
lines = p.read_text(encoding="utf-8", errors="replace").splitlines()
```
