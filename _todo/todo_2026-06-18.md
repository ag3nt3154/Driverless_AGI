## A. Bugs & Critical Issues

### A1. `_rebuild_for_normal_mode` missing `memory_root=` in `create_tool_registry` call (Priority: HIGH)

**File:** [`agent/loop.py:769-780`](agent/loop.py:769)

When `_rebuild_for_normal_mode` calls `create_tool_registry()` (lines 769-780), it does NOT pass `memory_root=self._effective_memory_root`. Compare:

- `__init__` (line 260): `memory_root=self._effective_memory_root` — **correct**
- `_rebuild_for_plan_mode` (line 846): `memory_root=self._effective_memory_root` — **correct**
- `_rebuild_for_normal_mode` (line 769-780): **missing** — falls back to `memory_root or cwd / "dagi-memory"` inside `create_tool_registry`

**Impact:** If the user has a custom `memory_root` in `config.yaml` (e.g., pointing to a shared wiki on a different drive), after a plan-mode → normal-mode transition, the `SkillTool` silently reverts to the default `project_path / "dagi-memory"` path. All skill-based memory operations (memory-add, memory-query, memory-ingest) would target the wrong directory for the rest of the session. This is the **exact same class of bug** that the `_build_preamble` refactor was meant to prevent — a rebuild method missing a parameter that `__init__` correctly passes.

**Fix:** Add `memory_root=self._effective_memory_root,` to the `create_tool_registry()` call in `_rebuild_for_normal_mode` (line 779, between `tracker=self.tracker,` and `bash_tool=self._injected_bash_tool,`):

```python
self.registry = create_tool_registry(
    cwd=self.config.project_path,
    allowed_roots=[dagi_root, self.config.project_path, self._effective_memory_root],
    skill_roots=skill_roots,
    plan_mode=False,
    plan_file=None,
    plan_mode_initiated_by="user",
    config=self.config,
    callbacks=self.callbacks,
    tracker=self.tracker,
    memory_root=self._effective_memory_root,  # ← ADD THIS
    bash_tool=self._injected_bash_tool,
)
```

This underscores the broader architecture issue (B1 from 2026-06-17): the 3 build sites diverge silently. A unified `_rebuild_system_prompt()` method would eliminate this entire class of bugs.

### A3. `BashTool.run()` doesn't handle `subprocess.TimeoutExpired` (Priority: MEDIUM)

**File:** [`tools/bash.py:25-37`](tools/bash.py:25)

When `timeout` is set and the command exceeds it, `subprocess.run()` raises `subprocess.TimeoutExpired`. This exception is NOT caught in `BashTool.run()` — it propagates to `ToolRegistry.dispatch()` which returns a generic `f"Error: {e}"`. The resulting error message is Python's default `TimeoutExpired` repr, which is not actionable for the LLM.

Additionally, the timed-out process is NOT killed — `subprocess.run()` raises after the timeout but leaves the child process running. On Windows, this can leak processes.

**Fix:**
```python
def run(self, command: str, timeout: int | None = None) -> str:
    if timeout is not None:
        timeout = max(1, timeout)
    try:
        result = subprocess.run(
            command, shell=True, capture_output=True,
            timeout=timeout, text=True, cwd=str(self.cwd),
        )
    except subprocess.TimeoutExpired:
        return f"[timeout after {timeout}s — command did not finish in time]"
    output = result.stdout + result.stderr
    if result.returncode != 0:
        output += f"\n[exit code {result.returncode}]"
    return output or "[no output]"
```

Note: `subprocess.run()` with `timeout` does call `proc.kill()` on timeout before raising, so the process leak concern is only for the `shell=True` case where the shell child may survive. A `os.killpg` improvement (already noted in TODO.md) would address this completely.

## B. Architecture & Consistency

### B1. `_system_breakdown()` reads disk on every Textual render cycle (Priority: MEDIUM)

**File:** [`tui/utils.py:58-70`](tui/utils.py:58), [`tui/sidebar.py:124`](tui/sidebar.py:124)

`Sidebar.render()` is called by Textual's compositor potentially many times per second. Each call invokes `_system_breakdown(dagi_root, project_path)`, which calls `_toks(path)` on 3 files — each one reads the file from disk, computes `len(text) // 4`, and returns. That's **3 file reads per render cycle**.

These files (main_system.md, soul.md, agents.md) essentially never change during a session. The token estimates are constant once the session starts.

**Fix:** Compute `_system_breakdown` once in `Sidebar.__init__` and store as `self._sys_parts: dict[str, int]`. Reference `self._sys_parts` in `_tokens_context_col()` instead of calling the function on every render. If `/wd` changes the project (which could change `proj/ag`), `set_project_path()` can recompute and update `_sys_parts`.

## C. Token Efficiency & Self-Improvement

### C1. Session cost is almost always `$—` (unreported) (Priority: HIGH)

**File:** [`agent/session.py:108`](agent/session.py:108)

```python
cost = getattr(usage, "cost", None) if usage else None
```

Most API providers (including OpenRouter for many models) do NOT populate `usage.cost`. The field is an OpenRouter extension that's only present for some models. This means `SessionTracker` records `cost=None` for most assistant turns, the sidebar shows `$—`, and the session_end record has `total_cost: null`.

Without cost visibility, there's no way to measure token efficiency improvements or compare model tiers.

**Fix (two-part):**
1. **Immediate:** Fall back to computing cost from token counts when `usage.cost` is None. Add a `pricing` section to `config.yaml` (per-model input/output cost per 1M tokens), and compute `cost = (input_tokens * input_price + output_tokens * output_price) / 1_000_000` in `record_assistant()`.
2. **Quick alternative:** Read `usage.prompt_tokens_details` which some providers populate even when `cost` is absent. At minimum, surface cached vs. uncached token counts (already noted in prior reviews as C1).

### C2. `on_done` doesn't distinguish clean completion from forced termination (Priority: LOW)

**File:** [`agent/loop.py:500-510`](agent/loop.py:500)

```python
if _exit_flag:
    ...
```

## D. New Features & Capabilities

### D1. `on_ask_user` in TUI callbacks has no deadlock protection (Priority: MEDIUM)

**File:** [`tui/callbacks.py:73-74`](tui/callbacks.py:73)

```python
safety = (timeout + 60) if timeout is not None else None
evt.wait(timeout=safety)
```

When `ask_user` is called with `timeout=None` (which is the default in plan mode via `AskUserTool.__init__`), `safety` is `None`, so `evt.wait()` blocks the agent thread indefinitely. If the TUI app crashes, hangs, or the user closes the terminal window while an `ask_user` prompt is pending, the agent thread hangs permanently — the daemon thread flag prevents it from blocking process exit, but any cleanup code after `run()` won't execute.

**Fix:** Always use a finite safety timeout:
```python
safety = (timeout + 60) if timeout is not None else 600  # 10 min max
```
After the wait, check if the container is still empty and return a fallback response rather than hanging.

### D2. `_tools_from_list` only supports 9 tool names — silently drops others (Priority: MEDIUM)

**File:** [`agent/tools.py:51-81`](agent/tools.py:51)

`_tools_from_list()` has a hardcoded `registry_map` with only 9 tools: `read`, `grep`, `find`, `write`, `edit`, `copy`, `bash`, `web_search`, `web_fetch`. If a `subagent_config.yaml` lists any other tool (e.g., `skill`, `ask_user`, `git_status`, `emote`, `switch_model`), it's silently dropped with a `[tools] Warning` on stderr that the user likely never sees.

This means subagent types can't use skills, ask the user questions, or access git tools — even when those would be useful for a review or worker subagent.

**Fix:** Either expand the registry_map to cover all tool types, or (better) drive subagent tool registration from the same `create_tool_registry()` function used by the main agent. Add a `tool_names: list[str] | None` filter parameter to `create_tool_registry()` and remove `_tools_from_list()` entirely. This was suggested in prior review (2026-06-16 A4) — elevating priority because the worker and review subagent types may actually need `skill` access.
