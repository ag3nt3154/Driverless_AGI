## A. Bugs & Critical Issues

### A1. Compaction failure crashes the entire session (Priority: HIGH)

**Files:** [`tools/compact.py:204-247`](tools/compact.py:204), [`agent/loop.py:588`](agent/loop.py:588)

When the summarization API call inside `compact()` fails (network error, rate limit, provider outage), the `except Exception` at line 245 rolls back the message list (correct) but then **re-raises the exception**. This propagates through:

1. `compact()` → raises
2. `_compact_context()` (line 362) → no exception handling, propagates
3. Main `while True` loop → caught by `except Exception as e:` at line 591
4. `callbacks.on_error(e)` fires, then `raise` → session dies

The messages are correctly restored (snapshot rollback), so the conversation is intact — but the session crashes anyway because the exception propagates. The user must restart.

**Impact:** A transient API error during compaction kills a potentially long-running session. This is especially likely when using OpenRouter (provider routing can fail mid-session) or when the context window is full (compaction is triggered precisely when the agent is under pressure).

**Fix:** Swallow the exception in `_compact_context()` and notify via callback:
```python
def _compact_context(self) -> CompactionResult:
    try:
        return self.compact_tool.compact()
    except Exception as exc:
        self.callbacks.on_assistant_text(
            f"[Warning: context compaction failed — {exc}. Continuing with full context.]"
        )
        return _NO_COMPACTION
```

This lets the agent continue with un-compacted messages. If the context is truly too large, the next API call will fail naturally with a context-length error, which the existing transient retry logic can handle.

### A2. Compaction dumps raw base64 image data into summarization prompt (Priority: HIGH)

**File:** [`tools/compact.py:56-74`](tools/compact.py:56)

When `ReadTool` reads an image, it returns a list: `[{"type": "image_url", "image_url": {"url": "data:image/png;base64,..."}}]`. This list is stored as the `content` of a tool result message. During compaction, `_format_messages_for_summary()` at line 69-72 does:

```python
elif role == "TOOL":
    lines.append(
        f"[TOOL RESULT tool_call_id={msg.get('tool_call_id', '')}]: {msg.get('content', '')}"
    )
```

When `content` is a list, Python's `str()` produces the Python repr: `[{'type': 'image_url', 'image_url': {'url': 'data:image/png;base64,iVBOR...'}}]`. A typical image is 100KB+ → 130K+ base64 chars → **~32,000 tokens** dumped into the summarization prompt.

**Impact:** A single image in conversation history can cause the compaction summarization call to exceed its context window, fail (see A1), and crash the session. Even if it doesn't fail, it wastes tens of thousands of tokens on the summarization call for content that can't be summarized as text.

**Fix:** Filter or truncate non-text content in `_format_messages_for_summary`:
```python
elif role == "TOOL":
    content = msg.get("content", "")
    if isinstance(content, list):
        content = "[image/multimodal content omitted from summary]"
    elif isinstance(content, str) and len(content) > 4000:
        content = content[:4000] + f"... [truncated, {len(content)} chars total]"
    lines.append(
        f"[TOOL RESULT tool_call_id={msg.get('tool_call_id', '')}]: {content}"
    )
```

## B. Code Simplification & Architecture

### B1. `_parse_frontmatter` is duplicated verbatim between `agent/skills.py` and `agent/workflows.py` (Priority: MEDIUM)

**Files:** [`agent/skills.py:30-42`](agent/skills.py:30), [`agent/workflows.py:30-42`](agent/workflows.py:30)

Both files define identical copies of:
- `_FM_RE` regex pattern
- `_KV_RE` regex pattern
- `_parse_frontmatter()` function (same signature, same body, same docstring)

Any bug fix or enhancement (e.g., multi-line YAML value support) must be applied in both places.

**Fix:** Extract to `agent/_frontmatter.py`:
```python
# agent/_frontmatter.py
import re

_FM_RE = re.compile(r"^---\s*\n(.*?)\n---\s*\n", re.DOTALL)
_KV_RE = re.compile(r"^(\w[\w-]*):\s*[\"']?(.*?)[\"']?\s*$", re.MULTILINE)

def parse_frontmatter(text: str) -> tuple[dict[str, str], str]:
    m = _FM_RE.match(text)
    if not m:
        return {}, text
    fm_block = m.group(1)
    body = text[m.end():]
    meta = {k: v for k, v in _KV_RE.findall(fm_block)}
    return meta, body
```

Import in both `skills.py` and `workflows.py`. One import, zero duplication.

### B4. `result_str` for tool results uses undocumented `__list__:` encoding (Priority: LOW)

**File:** [`agent/loop.py:555`](agent/loop.py:555)

```python
result_str = result if isinstance(result, str) else "__list__:" + json.dumps(result)
```

This `__list__:` prefix is a custom serialization convention used in JSONL logs (`ToolCallRecord.result`) and passed to `callbacks.on_tool_end`. It's undocumented — any downstream consumer (log parsers, analysis scripts, the `review-session` skill) must know this convention to handle image/multimodal tool results correctly.

**Fix:** Document in PROJECT_CONTEXT.md Notable Points. Or better: use a structured object `{"type": "multimodal", "content": [...]}` instead of a string prefix, so JSON consumers can handle it naturally.

## C. Token Efficiency & Self-Improvement

### C1. `thinking_tokens` (reasoning tokens) not recorded in session JSONL (Priority: HIGH)

**File:** [`agent/session.py:100-118`](agent/session.py:100)

`SessionTracker.record_assistant()` captures `prompt_tokens`, `completion_tokens`, and `cost` from the API response's `usage` object. But **reasoning/thinking tokens** (`completion_tokens_details.reasoning_tokens`) are NOT captured.

The TUI displays thinking tokens via `on_token_update` (line 486/574 of `loop.py`), but this value is computed locally and never reaches the session log. For models with extended thinking (DeepSeek, Claude with thinking enabled), reasoning tokens can be 50%+ of the completion token budget. Without logging them, post-session analysis of token efficiency is incomplete.

**Fix:** Add `thinking_tokens` to `MessageNode` and extract it in `record_assistant()`:
```python
thinking_tokens = None
if usage:
    ctd = getattr(usage, "completion_tokens_details", None)
    thinking_tokens = getattr(ctd, "reasoning_tokens", None) if ctd else None
```

Add to `MessageNode`:
```python
@dataclass
class MessageNode:
    ...
    thinking_tokens: int | None  # new field
```

The `session_end` record should also include `total_thinking_tokens`.

### C2. Tool result content not truncated in JSONL logs (Priority: MEDIUM)

**File:** [`agent/session.py:130-135`](agent/session.py:130)

`record_tool_end(name, result_str)` writes the full `result_str` to the JSONL log. For large tool results (file reads, grep output, base64 images via the `__list__:` encoding), this can be enormous. Compare with `record_subagent_end` at line 155 which truncates to 500 chars.

**Impact:** Session JSONL files grow rapidly. With 196 log files already, unbounded tool results are the primary driver of disk consumption.

**Fix:** Truncate `result_str` in `record_tool_end`:
```python
def record_tool_end(self, name: str, result_str: str) -> None:
    truncated = result_str[:2000] if len(result_str) > 2000 else result_str
    self._write(self._tag({
        "type": "tool_end",
        "name": name,
        "result": truncated,
        "result_length": len(result_str),
        "timestamp": _now(),
    }))
```

The full result is already in `ToolCallRecord` on the in-memory `MessageNode` (for `session_end.raw_messages`), so the truncation in JSONL records loses nothing for analysis.
